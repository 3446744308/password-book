## 1. 部署前必读：5 条硬约束

这些是架构决定的，不满足就会出问题，请先确认再动手。

| # | 约束 | 原因 / 后果 |
| --- | --- | --- |
| 1 | **只能跑 1 个实例** | 写队列是进程内串行、并发保护依赖 `data/.server.lock` 单实例锁。多进程或多副本会互相覆盖数据文件 |
| 2 | **`data/` 是全部数据和密钥** | 里面只有 JSON 文件；删掉 = 密码本作废。必须持久化 + 定期备份 |
| 3 | **远程访问必须 HTTPS** | 主密码在 `POST /auth/login` 请求体里明文传输；且刷新令牌 Cookie 只有在 HTTPS 下才带 `Secure` |
| 4 | **用反代时必须设 `X-Forwarded-Proto` 且配 `TRUST_PROXY=true`**；**IP 直连时必须为 `false`** | 前者缺了会导致 `req.secure=false`、刷新令牌 Cookie 不带 `Secure`；后者设成 true 会把 `req.ip` 取错，审计与限速都记错来源（均可实测复现） |
| 5 | **`AUTH_MODE` 必须在首次初始化前定好** | 模式写入 `data/secrets.json`，之后改环境变量无效；切换需要重建库或全量重加密（当前无脚本） |

> 前端 `web/dist` 由 Express 托管，**只需开放一个端口**，不需要单独跑 Nginx 之外的静态服务。
> `web/dist` 的存在性在**启动时检测一次**——先构建再启动，顺序反了会白屏。

## 2. 环境要求

| 项 | 要求 | 备注 |
| --- | --- | --- |
| Node.js | ≥ 18，推荐 22 LTS | 用到 ESM、顶层 await、`fs/promises`、`node:crypto` |
| 操作系统 | Linux（推荐）或 Windows | 本文主线为 Linux + systemd + Nginx |
| 内存 | 128 MB 起 | 单进程 Express，无数据库 |
| 磁盘 | 10 MB + 数据量 | 1 万条目约 10 MB |
| 反向代理 | Nginx 1.18+ | 负责 TLS 与端口收敛 |
| 端口 | 对外仅 80/443 | 应用端口 `3100` 只绑回环 |

**目录规划（本文示例）**

```
/opt/password-book/              # 代码（只读即可）
├─ server/  web/  scripts/  docs/
└─ server/.env                   # 生产配置（权限 600）
/var/lib/password-book/data/     # 数据（可写，权限 700，属主 passwordbook）
```

## 3. 部署步骤

### 3.1 准备系统用户与目录

```bash
sudo useradd --system --create-home --shell /usr/sbin/nologin passwordbook
sudo mkdir -p /opt/password-book /var/lib/password-book/data
sudo chown -R passwordbook:passwordbook /opt/password-book /var/lib/password-book
sudo chmod 700 /var/lib/password-book/data

sudo -u passwordbook git clone <仓库地址> /opt/password-book    # 或用 rsync 上传
```

### 3.2 安装依赖并构建前端

```bash
cd /opt/password-book

sudo -u passwordbook npm --prefix server ci
sudo -u passwordbook npm --prefix web ci
sudo -u passwordbook npm --prefix web run build      # 生成 web/dist（启动前必须完成）
```

> 部署前建议先在本机跑一遍质量门禁（CI 里也应保持一致）：
> `npm --prefix server test`、`npm --prefix server run lint`、`npm --prefix web test`、
> `npm --prefix web run typecheck`、`npm --prefix web run build`、`npm --prefix server run format:check`。

### 3.3 写配置文件

```bash
# 方案 A（Nginx 反代）：用通用示例
sudo -u passwordbook cp /opt/password-book/server/.env.example /opt/password-book/server/.env
# 方案 B（IP 直连，见 §3.8）：用生产模板，默认值就是直连配置
# sudo -u passwordbook cp /opt/password-book/server/.env.production.example /opt/password-book/server/.env
sudo -u passwordbook chmod 600 /opt/password-book/server/.env
sudo -u passwordbook vim /opt/password-book/server/.env
```

生产建议内容（只列与默认值不同的项，其余保持默认）：

```dotenv
NODE_ENV=production
HOST=127.0.0.1
PORT=3100
DATA_DIR=/var/lib/password-book/data
AUTH_MODE=strict
TRUST_PROXY=true
LOG_LEVEL=info
# CORS_ORIGINS 无需配置：前端与 API 同源（都由本服务提供）
```

配置项完整说明见 [§4](#4-配置参考)。

> `.env` 只在**环境变量未设置时**生效（见 `server/src/config.js` 的 `loadDotEnv`）。
> 用 systemd `Environment=` 设过的变量优先级高于 `.env`。

### 3.4 首次启动与初始化

先手工前台启动一次，确认能起来：

```bash
sudo -u passwordbook sh -c 'cd /opt/password-book && node server/src/server.js'
```

看到 `server.started` 日志即成功。**立刻**用浏览器访问 `https://<你的域名>/`
（若还没配 Nginx，先在本机 `curl http://127.0.0.1:3100/api/v1/system/health` 验证），
首次会进入 `/setup` 创建主密码，同时自动写入 7 个内置分类。

> ⚠️ **主密码没有找回机制**。忘记 = 数据作废，请当场离线记录。
> 初始化时如果 `AUTH_MODE=strict`，字段密钥只由主密码派生，磁盘上没有明文密钥。

确认无误后 `Ctrl+C` 停止（会释放 `data/.server.lock` 并 flush 日志），交给 systemd 托管。

### 3.5 验证清单

```bash
# 健康检查（无需鉴权）
curl -s http://127.0.0.1:3100/api/v1/system/health
# 期望：{"data":{"status":"ok","version":"1.0.0","schemaVersion":1,"initialized":true,"dataDirWritable":true,...}}

# 系统状态（无需鉴权）
curl -s http://127.0.0.1:3100/api/v1/system/status

# 明文扫描：确认落盘数据里没有明文密码
sudo -u passwordbook npm --prefix /opt/password-book/server run scan

# 断言文档与实现一致（部署的代码与文档没被改乱）
sudo -u passwordbook npm --prefix /opt/password-book/server run check:api-doc
```

浏览器侧确认：

- [ ] `https://<域名>/` 能打开并停留在解锁页
- [ ] 开发者工具 Network 里刷新令牌 Cookie 带 `Secure`、`HttpOnly`、`SameSite=Strict`
- [ ] 登录后新建/编辑/删除条目正常
- [ ] 刷新页面**不需要**重新输入主密码（见 §10 的 strict 模式例外）

### 3.6 交给 systemd 托管

```ini
# /etc/systemd/system/password-book.service
[Unit]
Description=Password Book (personal password manager)
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=passwordbook
Group=passwordbook
WorkingDirectory=/opt/password-book
EnvironmentFile=/opt/password-book/server/.env
ExecStart=/usr/bin/node /opt/password-book/server/src/server.js
Restart=on-failure
RestartSec=3
# 优雅退出：释放 data/.server.lock、flush 日志
KillSignal=SIGTERM
TimeoutStopSec=15

# 最小权限加固
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/password-book

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now password-book
sudo systemctl status password-book
sudo journalctl -u password-book -f
```

> `ReadWritePaths` 必须是 `DATA_DIR` 的实际路径；`ProtectSystem=strict` 会把其余路径设为只读
> （代码目录因此只读，符合预期）。若 Node 不在 `/usr/bin/node`，改 `ExecStart`。

### 3.7 【方案 A】Nginx 反代 + HTTPS（推荐）

```nginx
# /etc/nginx/sites-available/password-book
server {
    listen 80;
    server_name book.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name book.example.com;

    ssl_certificate     /etc/letsencrypt/live/book.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/book.example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    add_header Strict-Transport-Security "max-age=31536000" always;
    add_header X-Content-Type-Options nosniff always;

    # 与 server 端的请求体上限一致（app.js 用 express.json({ limit: '1mb' })）
    client_max_body_size 1m;

    # 前端构建产物：文件名带 hash，可长缓存
    location /assets/ {
        proxy_pass http://127.0.0.1:3100;
        proxy_set_header Host $host;
        proxy_hide_header Cache-Control;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    location / {
        proxy_pass http://127.0.0.1:3100;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        # ★ 关键：没有它 req.secure 为 false，刷新令牌 Cookie 不会带 Secure
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
        # index.html 不缓存，保证发版后立刻生效
        proxy_hide_header Cache-Control;
        add_header Cache-Control "no-store";
    }
}
```

```bash
sudo ln -s /etc/nginx/sites-available/password-book /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

**证书**：`sudo certbot --nginx -d book.example.com`（首次可先用 §3.4 的 http 方式跑通再上 TLS）。

> CORS：前后端同源时**不需要**配置 `CORS_ORIGINS`。若你把前端单独部署到另一个域名，
> 才需要把它加入 `CORS_ORIGINS`（逗号分隔、禁止 `*`），并放开凭证。

### 3.8 【方案 B】不用反代：用「服务器 IP + 端口」直连

适用：内网机器、自己独占的服务器、只想先跑起来看效果。

> ⚠️ **代价必须知情**：没有 TLS。主密码在 `POST /auth/login` 请求体里**明文过网**，
> 刷新令牌 Cookie 也拿不到 `Secure`。**不要在公共网络或多人共用的网络里这样跑。**

**1）写配置（模板已备好）**

```bash
cp server/.env.production.example server/.env
chmod 600 server/.env
# 模板默认就是 IP 直连：HOST=0.0.0.0 / NODE_ENV=production / AUTH_MODE=strict / TRUST_PROXY=false
```

**2）放行防火墙端口**（默认 3100）

```bash
# Linux (ufw)
sudo ufw allow 3100/tcp
# Windows（管理员 PowerShell）
New-NetFirewallRule -DisplayName "PasswordBook" -Direction Inbound -LocalPort 3100 -Protocol TCP -Action Allow
```

**3）前台启动并验证**

```bash
node server/src/server.js
# 另开一个终端
curl -s http://<服务器IP>:3100/api/v1/system/health
```

**4）浏览器访问** `http://<服务器IP>:3100`（首次进 `/setup` 创建主密码）

**实测行为**（`HOST=0.0.0.0` + `AUTH_MODE=strict` + `NODE_ENV=production`，见附录 B）：

| 检查 | 结果 |
| --- | --- |
| `GET /` 与深链 `/settings/config` | `200 text/html`（dist 正常托管） |
| setup → login → 创建条目 → 查看密码 | 全部通过 |
| 审计记录的来源 IP | 真实客户端 IP（如 `10.135.214.31`），不是 `127.0.0.1` |
| `secrets.json` | `mode=strict`，**无明文 `dek`** |
| 启动日志 | **无** `security.dev_mode.exposed` 告警 |

**三个容易踩的点**

1. **`HOST` 必须是 `0.0.0.0`**。保持默认 `127.0.0.1` 时，`127.0.0.1` 能访问、用服务器 IP 访问会「连接被拒」（实测返回 `000`）。
2. **`TRUST_PROXY` 必须 `false`**。直连没有代理，设成 true 会让 `req.ip` 取一个不存在的 `X-Forwarded-For`，审计与限速都记错来源。
3. **`AUTH_MODE=strict` 只对新建的库生效**。如果你把现有的 `dev` 模式库（`data/secrets.json` 里 `mode: "dev"`）搬到服务器，
   它会继续用 dev 模式并打印 `security.dev_mode.exposed` 告警——那种情况下 `data/` 里存着明文数据密钥。
   要么接受这个风险（仅内网），要么在服务器上重建库（当前库若只有测试数据，直接删 `data/` 重新初始化即可）。

**以后想升级成 HTTPS**：代码不用改。装好 Nginx 按 §3.7 配好，然后把 `.env` 改成
`HOST=127.0.0.1` + `TRUST_PROXY=true` 即可。

## 4. 配置参考

全部集中在 `server/.env`，由 `server/src/config.js` 读取；业务代码不直接读 `process.env`。

| 变量 | 生产建议 | 默认 | 说明 |
| --- | --- | --- | --- |
| `NODE_ENV` | `production` | `development` | `production` 下错误响应不回传堆栈 |
| `HOST` | 有反代：`127.0.0.1`<br>IP 直连：**`0.0.0.0`** | `127.0.0.1` | 默认只绑回环；IP 直连必须改 `0.0.0.0`，否则外部访问「连接被拒」 |
| `PORT` | `3100` | `3100` | 应用端口 |
| `DATA_DIR` | 绝对路径，如 `/var/lib/password-book/data` | `data` | 相对路径按仓库根解析 |
| `AUTH_MODE` | **`strict`** | `dev` | 见 §5 对比；仅首次初始化时生效 |
| `TRUST_PROXY` | 有反代：**`true`**<br>IP 直连：**`false`** | `false` | 让 `req.ip` / `req.secure` 取自 `X-Forwarded-*`；直连时开了会取错来源 IP |
| `CORS_ORIGINS` | 同源则留空 | `http://localhost:5173` | 逗号分隔白名单 |
| `JWT_SECRET_FILE` | 不设（用默认） | `jwt.secret` | 相对 `DATA_DIR`；首次启动自动生成，权限 600 |
| `ACCESS_TOKEN_TTL` | 不设 | `1800`（秒） | 仅是 `lockMinutes` 的**初值**；写入 `config.json` 后以配置为准 |
| `REFRESH_TOKEN_TTL` | 视风险定，如 `28800`（8 小时） | `604800`（7 天） | 「刷新页面免密」的窗口长度 |
| `KDF_ITERATIONS` | 不设 | `310000` | PBKDF2 迭代数；在**初始化与更换主密码**时写入参数，之后改环境变量不影响已有库 |
| `RATE_LIMIT_ENABLED` | 对外网可设 `true` | `false` | 关闭时无 429，暴力破解由失败锁定兜底 |
| `RATE_LOGIN_WINDOW_MS` / `RATE_LOGIN_MAX` | 不设 | `300000` / `5` | 仅 `RATE_LIMIT_ENABLED=true` 时生效 |
| `LOG_LEVEL` | `info` | `info` | `debug\|info\|warn\|error` |
| `LOG_TO_FILE` | `true` | `true` | 落盘到 `<DATA_DIR>/logs/app-YYYYMMDD.log` |
| `LOG_RETENTION_DAYS` | `14` | `14` | 启动时清理超期日志 |

**运行期配置**（`config.json`，通过「系统设置 → 系统配置」或 `PUT /system/config` 修改）：

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `lockMinutes` | 30 | 会话时长 = 访问令牌 TTL（改动只影响之后新签发的令牌） |
| `failedAttempts` | 5 | 连续失败多少次后锁定 |
| `lockMinutesAfterBan` | 15 | 锁定时长（分钟） |
| `minPasswordLength` | 10 | 主密码最小长度（只影响新设主密码） |
| `historyKeep` | 50 | 密码历史保留条数 |

## 5. `AUTH_MODE`：部署前必须做的决定

| | `dev`（默认） | `strict`（生产推荐） |
| --- | --- | --- |
| 字段密钥落盘 | **是**，`data/secrets.json` 存明文 DEK | 否，只存用主密码派生的封装（`dekEnc`） |
| 磁盘被拷走 | **可解密全部密码** | 无主密码不可解 |
| 服务重启后 | 免登录即可继续解密（DEK 在文件里） | **必须重新登录**才能解密字段（KEK 只在内存） |
| 更换主密码 | 秒级（只重封装 DEK） | 全量重加密（条目多时较慢） |
| 适用场景 | 仅本机自用、data 在可信磁盘 | 对外提供服务、备份可能外流、磁盘不完全可信 |

**关键事实（已实测）**：`strict` 模式下服务重启后，进程内没有字段密钥。持有未过期令牌的客户端会出现：

```
GET /entries        → 200   （列表不解密）
GET /entries/:id    → 401 TOKEN_INVALID「会话已失效，请重新登录」
GET /entries/:id/reveal → 401
```

这不是 bug，而是"主密码不进磁盘"的必然结果。前端拦截器会把用户带回登录页，
**每次重启后的第一次访问需要重新输入主密码**。

模式写入 `data/secrets.json` 的 `mode` 字段，运行期以它为准：
把 `AUTH_MODE` 从 `dev` 改成 `strict` 对**已初始化的库无效**。
切换需重建库（导出→重建→导入）或自己写重加密脚本，仓库当前不提供。

## 6. Windows 上运行（开发机自用可选）

Windows 没有 systemd。两种可行方式：

**A. NSSM 注册为服务**（推荐，能开机自启并自动重启）

```powershell
# 下载 nssm 后，在管理员 PowerShell 中：
nssm install PasswordBook "C:\Program Files\nodejs\node.exe" "D:\我的项目\密码本\server\src\server.js"
nssm set PasswordBook AppDirectory "D:\我的项目\密码本"
nssm set PasswordBook AppEnvironmentExtra NODE_ENV=production DATA_DIR=D:\pwbook-data AUTH_MODE=strict TRUST_PROXY=true
nssm set PasswordBook AppStdout "D:\pwbook-data\logs\stdout.log"
nssm set PasswordBook AppStderr "D:\pwbook-data\logs\stderr.log"
nssm start PasswordBook
```

**B. 任务计划程序**：触发器设为"计算机启动时"、操作里 `程序` 填 `node.exe`、
`参数` 填 `server\src\server.js`、`起始于` 填仓库根目录；勾选"不管用户是否登录都运行"。

> Windows 上同样只能跑一个实例。若用 NSSM 就别再手工 `node scripts/dev.js`（那是开发用的，
> 会同时拉起 Vite）。

## 7. 数据、备份与恢复

### 7.1 `data/` 目录内容

```
data/
├─ meta.json          # schema 版本与迁移记录
├─ config.json        # 运行期配置（会话时长、失败次数…）
├─ master.json        # 主密码校验值 + KDF 参数 + 失败计数（无明文）
├─ secrets.json       # 数据密钥（dev 模式含明文 dek！strict 模式只有 dekEnc）
├─ categories.json    # 分类 + 内置分类播种标记
├─ entries/*.json     # 每个分类一个文件
├─ history/*.json     # 每个条目一个历史文件
├─ jwt.secret         # JWT 签名密钥（0600）
├─ logs/audit.jsonl   # 审计日志（保留 1000 条）
├─ logs/app-*.log     # 运行日志（保留 14 天）
└─ backups/<时间戳>/   # 备份归档
```

> `master.json`、`secrets.json`、`jwt.secret` 与 `entries/` **必须一起备份**。
> 三份密钥材料缺一不可，否则数据不可解。

### 7.2 备份

```bash
# 手动
sudo -u passwordbook npm --prefix /opt/password-book/server run backup

# 或经 API（需要登录令牌）
curl -s -X POST -H "Authorization: Bearer $TOKEN" http://127.0.0.1:3100/api/v1/system/backup
```

备份落在 `data/backups/<YYYYMMDD-HHmmss>/`，自动排除 `backups/` 自身与 `.server.lock`。

**定时备份（cron）**——注意把 env 文件带上：

```cron
# 每天 03:10 备份，并把归档同步到异地
10 3 * * * cd /opt/password-book && set -a && . server/.env && set +a && \
  sudo -u passwordbook node scripts/backup.js && \
  rsync -a --delete /var/lib/password-book/data/backups/ /srv/offsite/pwbook/
```

> 服务端**不会自动清理旧备份**，请自行加保留策略（例如 `find ... -mtime +30 -delete`）。
> 备份里同样含密钥材料，**不要**放进任何第三方云同步目录。

### 7.3 恢复

```bash
sudo systemctl stop password-book
sudo -u passwordbook cp -a /var/lib/password-book/data /var/lib/password-book/data.broken
sudo -u passwordbook rm -rf /var/lib/password-book/data
sudo -u passwordbook cp -a /path/to/backup/<时间戳> /var/lib/password-book/data
sudo systemctl start password-book
curl -s http://127.0.0.1:3100/api/v1/system/health
```

- 恢复后 `jwt.secret` 也回来了 → 旧令牌仍然有效（想立刻失效就更换主密码）。
- 恢复完成后建议跑一次 `npm --prefix server run scan` 确认数据完整可读。

## 8. 升级流程

```bash
# 1) 先备份（迁移失败时可回滚）
sudo -u passwordbook npm --prefix /opt/password-book/server run backup

# 2) 停服
sudo systemctl stop password-book

# 3) 更新代码与依赖
cd /opt/password-book
sudo -u passwordbook git fetch --tags && sudo -u passwordbook git checkout <新版本>
sudo -u passwordbook npm --prefix server ci
sudo -u passwordbook npm --prefix web ci

# 4) 重新构建前端（不构建会继续用旧产物）
sudo -u passwordbook npm --prefix web run build

# 5) 启动（数据结构迁移在这里自动执行）
sudo systemctl start password-book
sudo journalctl -u password-book -n 50 --no-pager
```

**迁移行为**：启动时 `ensureSchema()` 对比 `meta.json.schemaVersion` 与代码内版本，逐个执行迁移，
并且**迁移前自动快照**到 `data/backups/pre-migration-vN/`；迁移失败会拒绝启动。

**回滚注意**：数据结构版本是单向的。用新版本启动过之后，再回退到旧代码会因
`meta.json` 版本更高而**拒绝启动**（日志：`数据结构版本高于当前程序支持版本`）。
所以回滚必须同时回退**代码**和**对应的 data 备份**：

```bash
sudo systemctl stop password-book
sudo -u passwordbook git checkout <旧版本>
sudo -u passwordbook rm -rf /var/lib/password-book/data
sudo -u passwordbook cp -a /path/to/backup/<升级前时间戳> /var/lib/password-book/data
sudo systemctl start password-book
```

## 9. 安全加固清单（逐项勾）

- [ ] `AUTH_MODE=strict`（对外提供服务时**强烈建议**；dev 模式磁盘被拷走即可解密）
- [ ] 全站 HTTPS，HTTP 301 跳转 HTTPS，启用 HSTS
- [ ] 反代设置 `X-Forwarded-Proto`，应用侧 `TRUST_PROXY=true`（否则刷新 Cookie 无 `Secure`）
- [ ] `HOST=127.0.0.1`；防火墙只放行 80/443，**不要**直接暴露 3100
- [ ] `data/` 权限 `700`、属主为服务账号；`server/.env` 权限 `600`
- [ ] 备份含密钥材料，离线/异地保存，不进入第三方云同步目录
- [ ] `REFRESH_TOKEN_TTL` 按风险设定（默认 7 天免密窗口）
- [ ] 对外网可选开启 `RATE_LIMIT_ENABLED=true`（默认关闭，靠失败锁定兜底）
- [ ] 给「连续失败锁定」准备恢复预案（见 §10 的锁定解锁）
- [ ] 定期看 `data/logs/audit.jsonl`（`ENTRY_REVEAL` / `HISTORY_REVEAL` 异常增多要警觉）
- [ ] 主密码离线记录，并确认备份可恢复（演练一次）

## 10. 观测与排障

### 10.1 日志在哪

| 位置 | 内容 |
| --- | --- |
| `journalctl -u password-book` | systemd 捕获的 stdout/stderr（与文件日志同源） |
| `<DATA_DIR>/logs/app-YYYYMMDD.log` | 结构化运行日志，单行 JSON，保留 14 天 |
| `<DATA_DIR>/logs/audit.jsonl` | 安全审计（登录、查看密码等），保留 1000 条 |

日志字段名含 `pass/secret/token/dek/kek/verifier/authorization` 的值会自动替换为 `[REDACTED]`。

### 10.2 常见故障

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 访问首页**白屏** | `web/dist` 不存在，或构建发生在服务启动之后 | `npm --prefix web run build` 后**重启**（启动时才检测 dist） |
| 用服务器 IP 访问**连接被拒/超时** | `HOST` 仍是默认 `127.0.0.1`（只监听回环），或防火墙没放行端口 | 改为 `HOST=0.0.0.0`（§3.8）并放行端口 |
| 启动即退出，日志 `lock.failed` | 另一个实例在跑 | 停掉旧进程；必要时删除 `data/.server.lock`（确认无进程占用） |
| 启动报 `数据结构版本高于当前程序支持版本` | 用新版本跑过又回退了旧代码 | 用配套的 data 备份一起回滚（§8） |
| `dataDirWritable: false` | 目录权限/属主不对 | `chown -R passwordbook:passwordbook <DATA_DIR>` |
| 刷新令牌 Cookie **没有 `Secure`** | 反代没传 `X-Forwarded-Proto` 或 `TRUST_PROXY` 未开 | 两者都配上（§3.7、§4） |
| 登录返回 `429` | 手动开启了限速 | `RATE_LIMIT_ENABLED=false` 后重启 |
| 登录返回 `423` 且密码正确 | 连续失败被锁定 | 等 `lockMinutesAfterBan` 分钟；急用见下方「锁定解锁」 |
| strict 模式重启后接口 `401 会话已失效` | KEK 只在内存，重启丢失 | 重新登录即可（§5） |
| 前端 403 / 请求被拦 | 前端独立域名未加入 `CORS_ORIGINS` | 加入白名单并放开凭证 |
| 备份报 `507 STORAGE_FULL` | 磁盘满 | 清理磁盘或旧备份 |

**锁定解锁（忘记等不了 15 分钟时）**：停服 → 编辑 `data/master.json`，把
`failedAttempts` 改回 `0`、`lockedUntil` 改成 `null` → 启动。

```bash
sudo systemctl stop password-book
sudo -u passwordbook python3 - <<'PY'
import json, pathlib
p = pathlib.Path('/var/lib/password-book/data/master.json')
d = json.loads(p.read_text())
d['failedAttempts'] = 0
d['lockedUntil'] = None
p.write_text(json.dumps(d, indent=2))
PY
sudo systemctl start password-book
```

> 这是**文档化的例外操作**：规范禁止手工改 `data/`，但锁定状态下无法登录改配置，
> 只能这样解锁。改完请立刻在「系统设置 → 系统配置」里把策略调成你记得住的值。

### 10.3 不要做的事

- ❌ 用 PM2 cluster / systemd 多实例 / K8s 多副本跑同一份 `data/`
- ❌ 把 `data/` 放在 OneDrive、iCloud、坚果云等同步目录（会产生冲突副本，破坏 JSON）
- ❌ 直接对外暴露 3100 端口（绕过 TLS，主密码明文过网）
- ❌ 只备份 `entries/`，漏掉 `master.json` / `secrets.json` / `jwt.secret`
- ❌ 在服务运行时手工编辑 `data/` 下的文件（审计与一致性都会乱）
- ❌ 把 `.env` 或 `data/` 提交进 git

## 11. 附录

### A. 最小验证脚本

```bash
#!/usr/bin/env bash
# 用法：./verify.sh http://127.0.0.1:3100
set -euo pipefail
BASE="${1:-http://127.0.0.1:3100}/api/v1"

echo "== health =="      ; curl -fsS "$BASE/system/health" | head -c 200; echo
echo "== status =="      ; curl -fsS "$BASE/system/status" | head -c 200; echo
echo "== 首页 =="        ; curl -fsS -o /dev/null -w '%{http_code} %{content_type}\n' "${BASE%/api/v1}/"
echo "== 未鉴权被拒 =="   ; curl -s -o /dev/null -w '%{http_code}\n' "$BASE/entries"   # 期望 401
```

### B. 本文档的验证边界

| 已验证（在本仓库实测） | 方式 |
| --- | --- |
| 生产模式下 Express 托管 `web/dist`，深链回退到 `index.html` | `NODE_ENV=production` 启动后请求 `/` 与 `/settings/about`，均为 `200 text/html` |
| 静态资源响应头为 `Cache-Control: public, max-age=3600` + `ETag` | 请求 `/assets/*.js` 看响应头 |
| 刷新令牌 Cookie 仅在 `X-Forwarded-Proto: https` + `TRUST_PROXY=true` 时带 `Secure` | 带/不带该头各登录一次，比对 `Set-Cookie` |
| `strict` 模式下 `secrets.json` 不含明文 `dek`，且重启后需重新登录才能解密 | 初始化→写条目→重启→对比 `GET /entries` 与 `/entries/:id` |
| 删掉 `data/` 后可重新初始化，且旧令牌失效 | `POST /auth/setup` 返回 201、旧令牌 401 |
| 默认无 IP 限速（无 429），由失败锁定（423）兜底 | 连续 7 次错误密码：401×4 + 423×3 |
| IP 直连可访问：`HOST=0.0.0.0` 时用局域网 IP 打开首页/深链/接口均正常；`HOST=127.0.0.1` 时用 IP 访问被拒 | 两种 HOST 各起一次，对比 `curl http://<LAN IP>:PORT/` 的返回码（200 vs 000） |
| 直连时审计记录的是真实客户端 IP；strict 模式无 dev 告警 | `POST setup/login/entries` 后查 `/system/audit` 的 `ip` 字段与启动日志 |

| 未在本环境验证（标准配置，需你在目标机确认） | 说明 |
| --- | --- |
| systemd unit、Nginx vhost、certbot 流程 | 本仓库开发机为 Windows，无法执行；语法为常规写法 |
| 定时备份 cron、异地同步 | 同上 |
| Windows 的 NSSM / 任务计划 | 仅给出步骤，未实际注册服务 |

> 附录内容按仓库内实现（`server/src/config.js`、`app.js`、`authService.js`、`crypto/index.js`）编写；
